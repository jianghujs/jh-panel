## Context

本设计面向计划任务的本地数据库备份执行链路，目标是消除本地清单过期造成的漏备份，并让失败结果可信。

| 位置 | 当前职责与问题 |
| --- | --- |
| `class/core/crontab_api.py` | 页面从插件 SQLite 读选库列表；根据类型生成 `scripts/backup.py` 调用 |
| `scripts/backup.py` | MySQL 固定走 `mysql-apt`；全部备份读本地 `databases`，单库也用本地记录判断存在性 |
| `plugins/mysql-apt/index.py::syncGetDatabases` | 查询 `SHOW DATABASES`，过滤系统库，只增补本地缺失记录，不删除陈旧记录 |
| `plugins/postgresql/index.py::syncGetDatabases` | 查询 `pg_database`，排除模板库和 `postgres`，同样只增补 |
| `class/core/mw.py::execShell` | Python 3 返回 stdout、stderr、returncode；当前数据库备份没有核对 returncode |
| `scripts/backup.py::cleanBackupByHistory` | 用 `type=1,pid` 查数据库备份，不区分两个插件各自的 ID 空间 |
| 数据库命令入口 | 结束时用 `cleanPath(..., '*')` 清理整个数据库备份目录，可能影响未成功备份的其他库 |

历史归档中的 `scheduled-database-backup-filtering`、`postgresql-backup` 作为任务参数、类型范围和文件格式的兼容依据；它们未出现在当前正式 specs 中，本次通过两个新能力记录执行期约束。

## Goals / Non-Goals

**Goals:**

- 全部备份的范围由每次执行时的服务器列表决定，新库自动纳入，已删库不再因本地旧记录被选中。
- 单库仅备份指定目标，不因缺少本地记录而误报服务器不存在。
- 保留现有数据库 ID、备注、账号字段及备份格式，为新发现的目标库按需补登记。
- 查询、登记、导出、打包/压缩失败有明确日志和非零命令退出状态，不误记成功，不以失败触发历史清理。
- 数据库历史清理限于本次成功备份的引擎及库，不影响网站、目录、插件配置备份逻辑。

**Non-Goals:**

- 不改计划任务页面及选库接口；页面仍可显示本地清单，执行时实时发现是此次保证点。
- 不自动清理插件陈旧记录，不同步账号密码、授权或改动服务器数据库。
- 不增加远程 MySQL/PostgreSQL 实例、多实例或其他 MySQL 插件支持。
- 不改 `backup_to != localhost` 的 FTP 等第三方备份插件执行链路；这些链路并非统一调用通用备份脚本，另行评估。
- 不新增表、依赖、后台同步任务或通用同步框架；不在本次实施完整恢复演练或内容级一致性验证。

## Decisions

### 1. 通用脚本直接调用插件方法，实时名单是唯一范围来源

按用户在实施阶段确认的职责调整，通用脚本通过独立模块名加载对应插件并直接调用其方法，不经过 HTTP 或重跑 UI 同步入口。插件提供 `prepareDatabaseBackup`、`getServerDatabases`、`ensureBackupDatabase`、`exportDatabaseBackup`；连接配置、系统库过滤和导出细节都留在插件，通用脚本仅负责调度、文件发布、成功记录与历史清理。UI 的“从服务器获取”复用同一个 `getServerDatabases` 查询方法。

共用的命令执行/超时回收和 SQLite 事务补登记放在 `class/plugin/database_backup.py`，两个插件调用，避免复制机械逻辑；不是新的同步框架。插件加载只执行模块定义，不调用初始化或服务操作。

- MySQL 插件：复用现有 `pMysqlDb()` 配置，执行 `SHOW DATABASES`；核验返回值是合法记录集合而不是异常对象，并通过 ORM 的可选读写超时限制名单查询等待，其他调用默认行为不变。
- PostgreSQL 插件：使用插件自带 `psql`，以与 `pg_dump` 相同的本机用户、端口和连接方式读取 `pg_database`。使用 `-X`、`ON_ERROR_STOP` 与机器可解析的 JSON 查询结果，避免格式化表格解析及额外认证差异。
- 两类查询使用有限等待；外部查询命令超时要终止并回收此次子进程，不能只抛异常而让子进程留在后台。错误、畸形结果与合法空列表分别处理。
- 名单获取完成后在内存保存本次快照，全部备份逐库复用，不为每个库重复查询完整列表。
- 查询和导出必须连接同一实例；构建 MySQL 导出命令时显式使用对应 socket 或 host/port，避免发现来自插件实例而导出落到系统默认实例。

替代方案：先调用 `sync_get_databases` 再读取 SQLite 改动小，但无法排除本地陈旧记录，并增加用户信息查询和同步响应解析依赖，因此不采用。完全绕过本地记录也不采用，因为现有备份登记仍依赖 `pid`。

### 2. 范围与系统库过滤保持清晰

| 调用范围 | 执行行为 |
| --- | --- |
| MySQL 全部 | 实时名单去重，排除 `information_schema`、`performance_schema`、`mysql`、`sys` |
| PostgreSQL 全部 | 实时名单去重，排除 `datistemplate=true` 的库和 `postgres` |
| 指定单库 | 查询验证指定名称，只处理该库，不同步或备份其他库；保留原有显式单库目标的可用性，不借全部备份过滤规则扩大限制 |
| 旧 `database backupAll` | 保留 MySQL 后 PostgreSQL 的既有类型范围，各类型采用实时名单 |

数据库名不作可改变名称含义的截断或大小写转换。SQL 条件使用绑定参数或固定目录查询后的精确比对；子进程参数和路径要安全传递，日志不输出密码。

保证边界为每个引擎取得名单的时刻，不承诺同时锁定数据库目录：快照后创建的库由下次任务纳入；快照后删除的库由实际导出失败识别。

### 3. 本地记录是关联元数据，不是存在性依据

服务器确认存在且属于本次目标后，按库名读取对应插件 `databases` 记录：已有记录原样使用，不更新 ID、备注、密码、用户和权限字段；缺失时复用插件现有补登记字段约定，写入库名、默认用户/访问字段、空密码、默认备注和创建时间，再读取有效 ID。只补本次目标，不调用创建库、建用户或授权接口。

插入前再次读取、插入后核对结果；并发任务已经补入的有效记录可复用，不盲目重复添加。无法得到唯一有效记录时明确失败，不继续以空 `pid` 登记或清理。无需为此改表结构或引入新的全局锁系统。

服务器已删库对应的本地记录保留，但不能进入全部备份名单。

### 4. 只有实际导出及封装成功才能记录成功

沿用现有压缩格式与文件名前缀，按当前分支分别验证：

| 分支 | 必须成功的阶段 |
| --- | --- |
| `mysqldump` | 导出与 `zstd` 管道（启用 `pipefail`） |
| `mydumper` | mydumper 导出；成功后才执行 tar 与 zstd；分别检查状态 |
| `pg_dump` | 导出与 gzip 管道；现有 `pipefail` 保留，但必须消费返回码 |

最终文件存在且非零是附加检查，不能替代退出码。合法空业务库也能成功备份，不以表数量或导出文件必须包含某类语句作判据。

失败时仅清理本次创建的临时目录和不完整产物，不写成功记录、不打印成功、不执行该库历史清理。使用本次独占的临时产物路径，成功后发布为既有最终文件格式，不能覆盖或误删以前的备份。若导出成功但备份记录写入失败，保留完整产物并记录路径，任务报错且不执行历史清理。

该校验保证工具报告成功，不等价于已经验证备份可恢复。

### 5. 失败状态和任务兼容

- 配置有效但查询失败：停止该引擎备份，不回退本地清单，返回失败。
- 查询成功但过滤后无业务库：明确记录数量为零，无导出、无补登记、无历史清理，返回成功。
- 全部备份所涉引擎未安装（插件本地配置库不存在）：保留已有显式跳过行为；配置库存在但配置损坏或缺失关键字段属于失败。指定单库缺少所需安装/配置则失败。
- 名单内某库登记或备份失败：记录具体库和阶段，继续同引擎其余库；最终汇总成功/失败数量，有失败则命令非零退出。
- 双引擎执行保留现有生成脚本 `set -e` 的先后与失败即停止策略；MySQL 命令失败后 PostgreSQL 可能不执行，不显示全任务成功。旧单进程 `database backupAll` 同样遵循此失败策略。
- 保留 `database`、`mysql_database`、`pg_database` 的原参数，兼容旧裸库名、`backupAll` 及类型前缀；通过公共脚本生效，不自动重写已有 crontab 文件。

日志提供类型、阶段、库名、名单数量或汇总；错误摘要需脱敏。无需为此改面板全局任务状态系统。

### 6. 清理必须限定当前成功库，不能只依赖 pid

为数据库清理传递引擎和库名上下文。在现有 `type=1,pid` 候选记录中，用已知前缀及完整时间戳后缀精确确认文件身份：MySQL 兼容 `mysql_` 与旧 `db_`，PostgreSQL 使用 `postgres_`。数据库名须按字面量匹配，不能把下划线、百分号或通配符当成模式，也不能把 `foo_bar` 当作 `foo` 的备份。候选路径必须位于备份目录内。

移除数据库命令尾部面向整个目录的 `cleanPath(..., '*')`；数据库文件和记录仅在对应库新备份及登记成功后，按原 `saveAllDay/saveOther/saveMaxDay` 规则处理。不能因一库成功清理另一库，也不在失败、空名单或跳过分支运行全局目录清理。非数据库备份分支保持原行为。

此处不迁移历史数据、不更改现有 `backup` 表结构，只收紧候选范围。无法可靠识别身份的文件保留而非猜测删除。

## Risks / Trade-offs

- [自动纳入新库会增加备份时间和空间] → 这是“全部备份”的预期语义，记录实时名单数量，保持指定单库范围不变。
- [数据库目录在执行中变化] → 使用运行期快照，后删库如实失败，后建库下次纳入，不承诺跨库原子备份。
- [插件查询封装可能返回异常对象而不抛出] → 显式验证结果类型、字段及空列表，用隔离测试覆盖。
- [两套插件的本地 ID 重复] → 数据库清理增加引擎及完整库名身份校验，不重构全局 ID。
- [停止全目录清理后陈旧库/孤立文件保留更久] → 为避免失败后删掉可用历史备份，本次保守保留；全局回收另设任务，不隐式执行。
- [实时查询和导出连接方式可能不同] → 每个引擎复用同一实例配置，测试非默认端口、socket 和本机用户切换。
- [直接加载插件入口可能有副作用] → 使用独立模块名，不执行 `__main__` 分支；隔离测试验证加载不会调用服务初始化、改库或运行真实命令。

## Migration Plan

1. 用临时 SQLite、临时备份目录、模拟查询与命令结果完成回归；不连接业务数据库、不运行真实清理。
2. 部署通用脚本及必要测试，不改任务参数、不自动清理插件记录，不要求重建任务。
3. 对已有任务脚本检查调用参数及退出状态传递，确认仍指向通用脚本；不自动改写生产任务文件。
4. 如需真实端到端验收，另经用户授权在测试实例创建/删除测试库，验证实时纳入、排除及错误反馈。
5. 回滚恢复本次业务代码版本；补登记记录和已完成备份继续保留，不通过删除数据库记录或备份文件回滚。

## Open Questions

无实施前必须确认的产品问题。本提案默认仅覆盖本地备份目标；FTP 等第三方备份目标，以及页面列表自动实时刷新，不纳入本次范围。
