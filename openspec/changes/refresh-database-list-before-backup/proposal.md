## Why

计划任务的数据库备份目前从插件本地 SQLite 清单读取备份范围，服务器上通过命令行或其他工具新增的数据库可能被漏备份，已删除的数据库也可能仍在清单中。备份任务需要以执行时的服务器实际列表为准，并避免导出失败却因压缩文件存在而记录为成功。

## What Changes

- MySQL（当前 `mysql-apt` 备份路径）和 PostgreSQL 的全部备份，在每次执行时查询对应服务器，过滤系统库后按实时名单逐库备份，不再由本地清单决定范围。
- 指定单库备份仅校验并备份指定库；服务器存在而本地未登记的库，按需补登记以兼容备份历史关联。
- 保留本地已有数据库记录、备注、账号信息和 ID，不自动删除服务器上已不存在的库对应的本地记录。
- 名单查询失败时明确报错且不回退旧清单；区分未安装、查询失败和查询成功但没有业务库。
- 核对 `mysqldump`、`mydumper`、`pg_dump` 及压缩/打包的实际执行结果，仅在成功时登记备份并进行对应库的历史清理。
- 保持现有任务类型、旧 `backupAll`、数据库类型筛选、备份格式和保留参数兼容，不要求重建已有任务。
- 本次只覆盖本地备份目标的通用执行链路，不修改页面列表刷新行为或 FTP 等第三方备份插件链路。

## Capabilities

### New Capabilities

- `database-backup-live-inventory`: 备份执行时的实时数据库发现、系统库过滤、单库校验、本地补登记、失败反馈及现有任务兼容。
- `database-backup-result-validation`: 数据库导出与压缩/打包结果校验、失败产物处理、成功记录及历史清理隔离。

### Modified Capabilities

无。当前 `openspec/specs/` 未登记计划任务数据库备份能力；历史归档中的类型筛选与 PostgreSQL 备份约束作为兼容依据，不修改归档文件。

## Impact

- 实现位置：MySQL/PostgreSQL 插件负责实时名单、补登记和导出，`scripts/backup.py` 直接调用插件方法并编排；`class/plugin/database_backup.py` 复用机械逻辑，MySQL ORM 增加可选查询超时；不新增第三方依赖。
- 复核 `class/core/crontab_api.py` 的任务生成与数据库备份命令退出状态传递；除必要的失败状态处理外，不修改页面或任务参数协议。
- 读取插件连接配置与数据库系统目录；仅为实时发现且本次需要备份的库补写本地 `databases` 记录，不修改服务器数据库、用户或权限。
- 使用现有 `backup` 表及文件名格式，限制历史清理作用于当前引擎、当前库；不新增表、不重构其他备份类型。
- 补充不连接真实业务数据库、不执行真实清理的隔离测试。
